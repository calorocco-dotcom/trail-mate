## 146K/294K 的统计口径

2026-10-12 用户在新固件上观察到 **144K/297K**，进一步要求降低分子。该值记录为用户实机观察；由于尚未取得同一页面、协议和网络状态下的精确字节快照，不把约 2K 的分子变化全部归因于某项优化。分子代表内部动态堆已用量，必须通过减少常驻动态分配、释放非活动对象或将适合的数据迁至 PSRAM 来降低，不能只修改显示口径。

随后用户在第二批优化固件重启后回报 **87K/297K**，并明确接受该优化。按要求在原页面比较，显示已用内部堆下降约 **57 KiB（39.6%）**，可用总量显示不变。此为用户实机粗粒度读数，尚非完整场景峰值和分配追踪；没有把全部收益精确归因到单一对象。COM69 实际 USB 握手、47 项能力、身份挑战验证及 309 字段配置读取通过，身份指纹/代数 1 保持一致，RF 配置仍为 Meshtastic。

memory_stats() 使用 MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT 获取内部可分配堆总量/空闲量；menu_runtime.cpp 显示总量减空闲量，按 1024 字节向上取整为 K。因此用户观察约为内部堆使用 49.7%，剩余约 148 KiB。它不是芯片全部 SRAM 的使用量，也不直接表示 PSRAM 使用量。

现有 ELF 的 .dram0.data 为 0x9f2c（40748 字节），.dram0.bss 为 0xe240（57920 字节），合计 98668 字节，与构建报告一致。该静态内存与屏幕内部堆的 146K 是不同口径。图标及字体的许多 nm D/d 符号位于 0x3c... flash 映射地址；不能只看 D/d 类型就把它们当作 RAM。

仅这个空闲快照无法证明峰值安全或存在泄漏；需要同场景比较内部 free、largest、minimum、DMA、PSRAM 及任务栈最低余量。工程已有 memory_diag 和 memory_budget 日志，但本轮没有获取当前固件的完整运行阶段测量。

## 针对已用内部堆的第二批优化

已修改源码，集中一次 Wio L2 构建验证：

1. Wio L2 普通 LVGL 分配优先 PSRAM，包括原来小于 2048 B、优先进入内部堆的按钮、标签、样式和管理对象。8 MiB PSRAM 可承载这些非 DMA 对象。显示 DMA 缓冲仍通过 beginLvglHelper 的显式 DMA 分配，既有严格 PSRAM UI/font lease 不回退内部堆，其他板型保留原阈值策略。普通分配在 PSRAM 失败时仍可回退内部堆以保持基础界面可用。
2. 有 PSRAM 的 Hostlink 发送帧使用 PSRAM 优先分配，降低 USB 活动时的内部堆峰值。四个最大长度帧的净数据上限为 4×522=2088 B；这是可能迁移的数据容量，不是空闲页面常驻节省，也未包含分配器开销。

测试直接编译从生产源码提取的分配及排队函数：Wio/其他板型分配策略、PSRAM 不可用或失败、严格分配、外部分配扩容不回退、零长度及释放，共两项 LVGL 原生测试；Hostlink 测试验证最大帧的实际内容/CRC/关联编号、队列满时丢弃与优先替换、申请失败、未就绪和释放，无新增任务或常驻大缓冲。三项 CTest 通过，ESP 栈检查通过。

此批尚未用实机证明具体节省量或界面流畅度。验收比较同一首页的内部 used/free/total 和 PSRAM 使用，另检查菜单、触摸、输入、轨迹/配置页面切换及重复进出后的回收；不能用静态 RAM 构建数证明 144K 已下降。任务栈、FreeRTOS 队列及 SDK 池的进一步缩减待最坏路径测量，不凭配置容量直接扣减。

此批 Wio L2 增量构建已成功，退出码 0，耗时 178.33 秒，静态 RAM 仍为 95,596 B，Flash 为 4,713,105 B；镜像 SHA-256 为 `f5715cd8356fae376dab73b11e4d6f4eba684e2d601848793a945ff71dc272c1`。实际 ELF 中 lv_malloc_core 已使用小对象 PSRAM 优先路径（0x404 为 SPIRAM|8BIT），不再按 2048 B 将普通小对象优先留在内部堆；Hostlink enqueue_event 已链接新分配实现。bzip2 两表仍在 0x3c… Flash 映射区。随后已从 COM67 上传 4,713,520 B，退出码 0、写入哈希通过；设备仍在下载模式，等待复位。144K 的实机变化及 UI 流畅度尚待确认。

静态表/静态缓冲减少通常扩大可分配堆总量，使屏幕分母增加，不必然使 146K 分子降低。动态对象迁移或栈缩减才会直接降低当前堆已用量。优化应比较空闲余量及最大连续块，而不是只追求分子下降。

SDK task.h 明确 uxTaskGetStackHighWaterMark 返回字节；当前 Xtensa StackType_t 是 uint8_t，现有乘 sizeof(StackType_t) 在此目标为乘 1，并非四倍误报。栈缩减必须使用匹配 SDK 的实际单位。

## 实施和验收顺序

先处理证据明确、风险低的只读表与重复常驻数据；同时准备轻量分阶段统计，避免用追踪器本身长期消耗 RAM。再评估 LVGL/HostLink、非活动服务和依赖缓冲，最后按实测缩减任务栈与 SDK 池。

首轮可把“净增加约 10–20 KiB 内部空闲余量”作为探索目标，而非已证明收益；目前只有 bzip2 的 3 KiB 表容量和 MSC 的可配置候选容量具有明确字节依据，不能承诺最终降低至某个屏幕数字。

集中一次构建和实机比较，覆盖空闲、配置读写、身份签名、Geocaching/轨迹、Wi-Fi/TLS、USB MSC 和协议切换。记录最低空闲、最大连续块、任务最低余量以及反复进入退出后的回收，不通过削减功能获得漂亮数字。
