# 配置服务在屏保与遮罩状态下的调度修复

2026-10-13，接50的第二次配置恢复后USB未及时重连调查。当前设备仍运行8bcf6607…，原配置已只读核验恢复，用户确认87K／297K及功能正常。

## 已确认的源码缺陷

Arduino串口命令在app runtime的屏保判断前处理，但serviceWorkingConfig原先在tickBoundLifecycle内。屏保、唤醒后750ms等待都会提前返回，跳过它。遮罩状态由loop_shell直接跳过整个app runtime，也会跳过配置服务。

因此，设备可以已经确认配置／身份提交及两秒后重启，却仍因屏幕状态无法执行延迟重启；设备菜单的待同步配置也可能被同一门禁阻挡。该问题由实际函数原生执行复现：带USB自动启动与不带USB自动启动两种测试均在屏保下未同步的断言失败。

此缺陷与串口固件下载模式不同，也不依赖当前RF协议。它可以造成管理重启等待，但尚不能证明它是上次端口消失的唯一原因；Windows枚举、硬件重启、启动阶段等仍须实机核对。

## 修复与资源约束

从Arduino tickBoundLifecycle移除配置服务调用，在Arduino主循环的loop_shell完成后、agenda之前统一调用。显示先呈现，配置服务仍在同一主循环任务中执行，屏保／唤醒等待／遮罩不会阻挡已接受的提交。串口断开后也会完成原有重启计划。

保持两秒确认窗口及一秒SD同步重试节流，不增加任务、队列、AppConfig副本、全局状态或缓冲区。IDF已有独立调度与显示锁保护，本次不改变它。正常前台每次循环只调用一次配置服务。
