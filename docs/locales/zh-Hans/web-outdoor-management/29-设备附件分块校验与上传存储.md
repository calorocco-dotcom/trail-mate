# 设备附件分块校验与上传存储

更新：2026-10-13。本批完成生产代码中的附件上传类型、分块索引/资源校验，以及短期 PSRAM 设备作业；尚未串入现有完整的轨迹准备、签名和文件保留状态机。不能把附件作业 Ready 当作轨迹已经签名、发布、安装或可以导航。

## USB 上传存储类型

复用现有 TransferBegin/Chunk/Finish/Status、双日志封存和身份绑定，不新增传输队列或常驻文件缓存。

| kind | 内容 | 单文件上限 | 设备生成目录 |
|---|---|---|---|
| 3 | 原 KML | 8 MiB | `/trailmate/web-upload` |
| 4 | 原清单 | 4096 字节 | `/trailmate/web-manifest` |
| 7 | 原 IP 回执 | 1100 字节 | `/trailmate/web-receipt` |
| 8 | 附件索引 | 294912 字节 | `/trailmate/web-index` |
| 9 | 附件资源 | 8 MiB | `/trailmate/web-asset` |

设备路径只由 kind 和非零 16 字节 upload ID 生成，不使用 KML 中的 URL、相对路径或作者文件名。资源候选的物理后缀沿用 `.cmp`，表示保存的字节，不是 MIME/图片解码结果。

单块仍最多 320 字节。类型值在转换成 uint8 前检查范围，264/265 不能截断成 8/9。新的 kind 仅进入本批源码，旧固件没有相应能力；网页附件流程尚未接入，不能从原有 Transfer 操作存在推断旧设备支持附件。

资源目录最多容纳 64 笔上传，每笔候选和两份日志，合计最多 192 个文件、64 MiB 资源字节加日志预算。未知文件、孤儿文件和目录项全部计入限制；不能靠忽略文件名释放配额。索引目录仍按两笔上传限制，原 KML/清单/回执目录的原配额保持。目录枚举 Impl 也只申请 PSRAM，失败返回 Busy，不退回内部 RAM。

这只是上传存储配额；最终包仍受 KML + 索引 + 所有声明资源合计 64 MiB、图片/role 限额及条目结构限制。资源目录的剩余空间不等于某个包可被接受。

## 分块索引与资源作业

`AttachmentIndexStream` 借用 4352 字节条目窗口和 64 个去重指纹槽；逐条处理，不持有整份索引。指纹只用于保守拒绝重复/碰撞，不是密码学物料或真实性证明。条目视图在 advance 后失效。

`AttachmentIndexFileCheck` 每次最多读取 320 字节，返回前关闭文件句柄。解析出条目时暂停，完整索引的实际长度、结构、KML 绑定和 SHA256 全部通过后才 Ready；提前解析出的条目是暂定视图。

`AttachmentPackageFileCheck` 在索引暂停时逐项校验资源，使用独立的第二个 SHA256 context，不能打断仍在累积的索引摘要。可用性用两个 64 位位图记录，不建立文件列表或资源正文缓存。

`SealedAttachmentUploads` 按索引顺序映射至冻结的 upload ID，核对双日志、Sealed 状态、当前作者摘要和代次、ID、大小及文件摘要。日志 CRC 不能代替重读候选的 SHA256。

- 非零 ID：必须有正确的封存日志和实际文件，即使该资源是可选，也不能将损坏/丢失的已提供上传当作正常缺省。
- 零 ID：明确没有提供该资源；必需项返回 MissingRequired，可选项保留部分可用状态。
- 索引/资源摘要错误、元数据矛盾或 I/O 错误：拒绝，没有任何头记录、签名或安装写入。

`TrackAttachmentPrepareOwner` 冻结作者、索引/KML 摘要、大小和最多 1024 字节 upload ID 映射；在单个短期 PSRAM owner 内运行这些校验。owner 大小以 <=9216 字节断言约束，SD Impl 另计。逐步确认当前身份和媒体，代次/作者/卡片改变即失败，取消和释放清理两份哈希作业。无新可变全局槽，没有大任务栈数组，也没有内部 RAM 申请回退。这个大小约束已通过原生编译，尚未通过本批 ESP SDK 编译或实机运行测量。

## 本批验证

原生测试编译实际 ESP owner、实际借用 SD adapter、双日志、上传/封存/恢复与真实 SHA256，底层 SD/堆为模拟。覆盖 64 项全部可用、可选缺失、必需缺失、必需/已提供可选文件损坏、索引损坏、缺少已提供上传日志、身份代次变化、换卡、取消、外部映射修改不改变冻结作业，以及 owner/SD backing 的 PSRAM 申请失败。

新 kind 的实际上传 owner 完成 641 字节跨三块传输、封存、释放后恢复；配额验证 64 资源目录容量与拒绝超额。校验前后源文件映射完全相同。6 项相关 CTest、2 项浏览器 CMP/原生解码互操作、ESP 栈和轨迹流式读取检查通过。格式化后的最终结果以本批测试日志为准。

不包含真实 USB、SD 设备、RNS 传输、图片格式解码、显示或掉电证据。本批不进行固件整包构建或刷写，运行 RAM 没有新的测量，用户验收的 87K/297K 仍是最近有效实机结果。

## 继续完成的接入

现有 PrepareRequest 仍是 KML/清单两个上传 ID；还需明确附件映射的 USB 编码及能力协商，冻结到同一准备任务，保持旧请求兼容。

接入时必须把 KML 几何/摘要、索引/资源校验、身份/媒体租约、签名准备记录以及 KML+附件的保留/安装恢复串成完整状态机。当前 ManifestFileCheck 的 v2 门禁保持，不能只把版本判断删掉而使 KML-only 检查授权完整包。

之后补网页的附件维护、缺失说明、多语言、完整包下载和设备安装流程，并统一进行 ESP 构建和实机/掉电验收。此文补充 [27](27-签名附件索引与版本演进.md) 和 [28](28-附件传输与目录保存核验.md)，不缩减完整 KML 交付范围。
