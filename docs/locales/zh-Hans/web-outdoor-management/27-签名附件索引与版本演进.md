# 签名附件索引与版本演进

更新：2026-10-13。三端协议基础实现与互操作验证完成；后续浏览器网络上传与目录索引/必需资源保存检查已贯通本地联调，详见 [28](28-附件传输与目录保存核验.md)。设备发布/安装及完整附件 UI 仍未贯通，下述目录 v2 门禁为实施历史状态，以 28 的最新记录为准。

## 已部署格式与新格式

实际 v1 清单为 14 字段、最多 4096 字节，只绑定 KML。其编码、签名域、版本摘要域和既有对象 ID 均保留。

v2 为 16 字段：前 14 字段的位置与 v1 相同，首字段改为 `2`，末尾分别为 `metadata` 与附件索引描述符 `assets`。主清单仍最多 4096 字节，KML 文件元组内的格式仍为 `1`。

```text
signature: Ed25519.Sign("TrailMate.Track.Manifest.v2\0" + raw_manifest)
revision:  SHA256("TrailMate.Track.Revision.v2\0" + raw_manifest)
object_id: SHA256("TrailMate.Track.ID.v1\0" + author_public_key + creation_nonce)
```

上式 signature 表示既有 Ed25519 过程的精确消息域，不另造预哈希签名算法。对象 ID 的域保留 v1，使同一作者/nonce 的对象在清单升级后仍可用原 ID 分享。新版本链可从 v1 升到 v2，拒绝 v2 降回 v1；归档必须保持 KML 和附件索引绑定，不能借归档删除或替换附件。

## metadata

```text
[activity:u8, tags:[str], geometry_capabilities:u32,
 segment_count:u32, waypoint_count:u32,
 time_coverage:u8, altitude_semantics:u8,
 derived_from:[object_id:bin32,revision_hash:bin32]|nil]
```

- activity 使用 u8；界面分类映射与目录筛选仍待接入。
- tags 最多 8 项，每项最多 48 UTF-8 字节，要求有效非空文本，不允许精确重复。
- geometry_capabilities 为 u32；两个数量分别不得超过主清单点数。
- time_coverage 为 0..2，altitude_semantics 为 0..4；具体几何与高度解释必须由 KML 读取核验，不将作者标注当作设备推导结果。
- derived_from 为来源声明。源对象的作者与当前性仍须独立验证。

## 附件索引

08 中把全部附件直接放入主清单的草案改为摘要寻址的索引文件。这使 64 项完整引用不挤占 4KB 签名/控制消息，也不要求设备常驻附件表。索引摘要受作者签名保护，每个资源的精确摘要和引用又受该索引保护。

```text
assets = nil | [index_sha256:bin32,index_bytes:u32,entry_count:u8,index_format=1]
index  = [1,kml_sha256:bin32,kml_bytes:u32,entries:[entry]]
entry  = [asset_id:str,file_sha256:bin32,file_bytes:u32,mime:str,
          kml_reference:str,role:u8,required:u8]
```

required 的应用语义为是否必需，CMP1 线上编码用 0/1，保持现有确定性类型子集；不引入 MessagePack bool。role 为 0 描述图片、1 路标图标、2 叠加图片、3 其他文件。

当前初始硬上限：64 项附件；索引 294,912 字节；每项引用 4096 UTF-8 字节；ID 最多 48 ASCII 字符且仅字母/数字/下划线/连字符；MIME 最多 96 字节；图片或 role 0..2 单项最多 4 MiB，其余单项最多 8 MiB。KML、索引和全部条目声明大小合计最多 64 MiB。后续节点能力公告和设备空间预检必须使用相同或更严格预算，不能据此保证当前节点已有足够空间。

ID 拒绝 FAT 大小写冲突，精确引用拒绝重复。相对引用拒绝绝对路径、反斜杠、点段、百分号编码穿越/路径分隔符/控制字符；HTTP(S) 引用保持原文，不自动访问。索引字段不能直接充当磁盘路径，导出/安装仍须做实际目标路径及内容类型检查。

索引校验要求主清单声明的 hash/bytes/count 与实际索引一致，同时核对 KML hash/bytes、每项编码/预算及完整 EOF。它证明索引与清单绑定，不能单独证明作者身份、资源文件存在或设备安装完成。

## 内存与实施边界

设备主 ManifestView 只在原有尾部填充内增加版本和扩展偏移，不扩展其 ABI 大小；编译期断言按实际对齐计算。扩展视图/条目视图借用字符串和摘要，不复制内容或建立附件数组。主解码器可以不构造扩展输出对象，仅验证字段。

当前 AttachmentIndexCursor 借用完整不可变输入并逐条读取，重复检查重扫此前条目；它自身不申请索引缓冲，不代表 SD 文件流已经接入。后续设备作业须使用受限条目窗口和存储租约，或者明确准入的短期 PSRAM backing；不能把完整索引放入任务栈或内部堆。

目前设备 ManifestFileCheck 与目录 DirectoryIndex.publish 均拒绝 v2 的完整发布/安装预检，直到索引、必需资源和安装事务真正贯通。密码学原语的 v2 签名/验签已实现，不等同于已经开放设备发布接口。旧 v1 流程保持可用。

下一步必须完成：按 hash 上传索引及资源、目录必需/可选文件检查与可用性状态、设备索引流式校验与准备记录绑定、浏览器附件维护/恢复、多语言交互、KML+必需附件原子安装及显示；仍保留完整 ZIP 导出、资源路径冲突、断线/磁盘满/掉电和实机验收。

## 验证证据

浏览器/C++/Python RNS 真实 Ed25519 和 SHA 互操作通过：v2 签名及摘要一致、C++ v1/v2 签名可被另外两端验证、v1 固定编码向量未变、升级保留 ID、降级及归档附件更换被拒绝。64 项/每引用 4096 字节的索引通过，同时主清单保持小于 4096 字节。

反例包括错误 KML/索引摘要和大小/数量、非法 MIME、必需标记编码、重复 ID/引用、大小写冲突、穿越与危险 scheme、容量越界、截断/尾随数据及非法元数据。发布预检测试确认合法 v2 也不会仅凭 KML 进入 Ready，目录版本表/头表不发生写入。

当前通过 15 项 Node/三端互操作、8 项相关原生 CTest（含实际 SDK metadata owner 的原生编译/运行）、Python 协议/目录/生命周期/几何 7 项回归，轨迹网页构建和 ESP 栈检查。ABI 自检曾错误写死 64 位大小，已改为实际对齐断言并通过；不是固件运行 RAM 的测量。此批未 SDK 构建/上传，没有实际网络附件或 SD/掉电验收。
