# 电脑目录有界大块文件传输

2026-10-14，接105。核对大文件流程时，原IP文件上传／下载每块1024字节、逐请求等待确认；8MiB单文件单向需要8192次分块请求。本批实现显式可选的4096字节传输，将同样文件的分块请求数降至2048，不以此推断实际时间必然缩短四倍。完整8MiB／64MiB网络压力验证仍待，不能将下述原生存储或小文件真实网络回归推广。

## 协议与兼容

普通能力0空体及4／5／6／8保持原数据形状和1024字节上限。只有扩展能力0的[2]查询列出新命令19；电脑客户端依经过身份与epoch绑定的能力自动选择，旧目录继续走原路径，USB／固件接口没有修改。

命令19是电脑目录文件传输扩展：

| 子命令 | 请求body | 成功body |
| --- | --- | --- |
| 0，开始／续传 | [0,sha256,size] | [token或nil,offset,sealed,4096] |
| 1，写块 | [1,token,offset,bytes] | [token,nextOffset] |
| 2，读块 | [2,sha256,offset,length] | [sha256,total,offset,bytes] |

封存仍使用命令6，作者签名、索引、发布请求ID和回执规则不变。请求／回复保持8192字节CMP1预算，不放大公共解码预算或引入无界块。原数据和大块共享同一上传token、认证来源、偏移、到期、摘要与SQLite检查点；不同来源不能写同一token，既有小块上传可从原偏移继续。

BlobStore只有明确的内部max_chunk=4096调用可使用大块；默认1024及旧操作保持。重复块须与已提交字节完全一致，写入先flush／fsync再提交检查点，重开按原检查点恢复，不提前推进。

网页发布协调器将此能力传给KML、附件索引和资源上传。TrackDirectoryClient的直接读取与IP只读适配器使用4096字节读取；工作台详情／完整包／维护已经使用适配器的chunkBytes，因而接通。通用读取器仅扩大可接受的有限chunkBytes上限，默认仍1024。

IP只读适配器对原命令8内部转换为19子命令2，不对调用者开放19；19的写入子命令及原写命令依旧拒绝。不得因为一个扩展操作同时含读写而绕过原只读边界。

## 已验证

- 新3项Node：8MiB上传从非对齐3072偏移继续，每块最多4096、尾块和摘要保持；旧默认仍8192次1024块；错误协商／取消无封存；只读适配器只能转换读操作，原始19及5写入拒绝，关闭后不再发请求。
- 原12项读取／包／IP适配器Node退出0，网页构建及差异检查通过。
- 新真实原生存储专项退出0，耗时58.724秒：8MiB确定字节模式的文件按2048个4096块写入，2MiB处关闭重开SQLite／文件存储后原token及偏移恢复；重复一致块接受、不同字节拒绝；跨身份／4097字节／旧5大块及旧8大块拒绝；封存和逐块读取原SHA核对、过小回复预算413与8192字节预算检查通过。
- 首次专项末尾将CMP1不允许的bool子命令误判为422；实际解码在分发前拒绝。修正为应当拒绝解码，并用ExitStack保证异常时SQLite在临时目录清理前关闭后重跑通过。没有修改生产解码规则。专项是opaque blob，不冒充8MiB KML解析／签名出版验证。
- 原8项应用／存储／附件，以及22项存储故障／复制／服务回归退出0。
- 实际浏览器RNS／LXMF／raw桥和两个生产目录回归退出0，27.080秒、140个请求、中位121ms／P95 171ms；新19实际请求及回复出现在日志。包括独立作者与传输身份、创建／原ID重试／地图及四级行政区／精确KML和PNG／更新／归档、两目录重启、新阅读者身份和历史读取。该样本约3KiB KML及小PNG，证明新能力经真实网络可用，不是最大文件或最大包验证。
- 结果在`.codex-build/hostlink-codec/track-network/result.json`，日志在track-network-current.log；新专项加入CI但没有远端运行。当前Node／Python源改动不涉及固件或设备RAM。
