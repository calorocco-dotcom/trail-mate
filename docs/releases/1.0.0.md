## Decentralization and privacy

Users control their device identity and local records without handing their
complete private trail history to one account platform. The browser uses the
device's author identity over USB, while the computer carries Reticulum network
requests. Changing the device's chat/RF protocol is not required. Independent
operators can provide directories and gateways, and recipients can verify
author signatures independently.

This reduces the need for one platform to collect and correlate everyone's
activity, but does not guarantee that public information cannot be retained or
analysed. Published routes, coordinates, timestamps, public keys and metadata
are visible to directories and recipients. Publications under the same author
can be linked. Gateways and external map providers can observe connection or
map-request metadata. Archiving changes publication state; it cannot withdraw
historical copies already held by others.

The README and Wiki must not claim that no platform can ever learn a user's
trails or behaviour. Explain which data stays local, what users choose to share,
and what recipients can see.

## Required firmware card views

Apply Contacts' reused single-card and on-demand hydration approach to Tracker
and Geocaching. Before the change, Tracker recreated buttons for up to 32 recordings
or 64 routes, while Geocaching already read a small window, so their potential
benefits differ. Reuse one card and its widgets, hydrate only the selected item,
and open images/details on demand. Avoid parsing KML for every item or retaining
prefetched item data. Keep a lightweight navigation index and preserve selection
by file identity or cache ID when records refresh.

Keep existing Tracker recording/route categories and Geocaching sections and
actions. Show previous/next navigation and the current position in the result
set. Support the existing touch, keyboard and encoder inputs. Populate richer
summary fields only when the current item supplies them; do not scan all KML
files to manufacture card statistics. Reuse the existing Contacts interaction
and styling rather than introducing another card framework.

Acceptance requires working selection, details and existing actions, constant
card-widget count as the directory grows, and on-demand reads for the current
item. Report measured resource changes; do not infer a RAM saving from visual
appearance alone. The implementation and complete native Tracker-page validation
are present. The latest Wio navigation/menu visuals, touch and actual following
were accepted by the user on October 16; the physical Geocaching publication and
archive evidence is recorded above.
